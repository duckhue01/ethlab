📦 BeaconBlock Structure (Electra / Pectra body, current on Fusaka)

Pectra moved deposits into execution_requests and added BLS-to-execution credential changes. Blob commitments stay on the beacon block; the blob data itself is custody-sampled via PeerDAS.

End-to-End Consensus Flow

From transaction submission to finalization

1
EL

Transaction Submitted

User sends a signed transaction via eth_sendRawTransaction to an EL node.

// geth: internal/ethapi/transaction_args.go
User → JSON-RPC :8545 → TxPool.Add(tx)
// Validates: signature, nonce, balance, gas limit
// Sorts by: EIP-1559 effective tip
2
EL

Transaction Gossip (devp2p)

Transaction propagates across the EL peer-to-peer network.

// geth: eth/protocols/eth/handler.go
EL Node A → eth/69 NewPooledTransactionHashes → EL Node B
EL Node B → GetPooledTransactions → fetches full tx
// All EL nodes now have the tx in their mempool
3
CL

Slot Begins — Proposer Selected

Every 12 seconds a new slot starts. Proposer selection is weighted by effective balance and driven by RANDAO. Since Fusaka, EIP-7917 exposes a deterministic proposer lookahead for the next epoch.

// consensus-specs: phase0/beacon-chain.md
proposer_index = compute_proposer_index(
  state, epoch, RANDAO mix
)
// Weighted by effective balance (32–2048 ETH, Pectra)
// Fusaka EIP-7917: proposer lookahead for next epoch
// → enables based preconfirmations
4
ENGINE API

CL Requests Payload from EL

The CL calls the Engine API to ask the EL to build an execution payload. getPayload versions track the fork (Pectra V4, Fusaka V5); newPayloadV4 stays current until Glamsterdam.

// Step A: Signal fork choice + start building
CL → engine_forkchoiceUpdatedV3({
  headBlockHash: "0xabc...",
  safeBlockHash: "0xdef...",
  finalizedBlockHash: "0x123..."
}, payloadAttributes: {
  timestamp, prevRandao, suggestedFeeRecipient,
  withdrawals, parentBeaconBlockRoot
}) → returns payloadId

// Step B: Retrieve the built payload (Fusaka)
CL → engine_getPayloadV5(payloadId)
  → ExecutionPayloadV3 + blockValue
  → blobsBundleV2 (blobs + cell proofs)
  → executionRequests

// geth: eth/catalyst/api.go → miner/worker.go
5
EL

EL Builds ExecutionPayload

The EL selects transactions from the mempool, executes them through the EVM, and produces a payload. Fusaka raised the default block gas limit to 60M and capped a single transaction at 16.7M gas.

// geth: miner/worker.go
1. Select highest-tip txns from TxPool (legacy + blob + 7702)
2. Execute each tx through EVM (core/vm/)
3. Apply state transitions → new stateRoot
4. Compute receiptsRoot, gasUsed, logsBloom
5. Include withdrawals + blob gas accounting
6. Collect EIP-7685 executionRequests
7. Package as ExecutionPayloadV3 (≤ 60M gas/block)
6
CL

CL Assembles & Signs BeaconBlock

The validator client wraps the ExecutionPayload in a BeaconBlock and signs it with BLS.

BeaconBlock = {
  slot, proposer_index, parent_root, state_root,
  body: {
    randao_reveal: BLS_sign(epoch),
    attestations: [...from previous slots...],
    sync_aggregate,
    bls_to_execution_changes: [...],
    execution_payload: /* from EL */,
    blob_kzg_commitments: [...],
    execution_requests: { deposits, withdrawals, consolidations },
  }
}
signature = BLS_sign(BeaconBlock)
7
CL

Block Broadcast (libp2p GossipSub)

The signed BeaconBlock is broadcast to all CL peers via GossipSub, together with the blob data columns introduced by Fusaka's PeerDAS.

Proposer → gossipsub:/beacon_block → All CL Nodes
// Fusaka: blobs split into 128 column subnets
// + /data_column_sidecar_{subnet} (PeerDAS)

// Each receiving CL node:
1. Verify proposer signature (BLS)
2. Verify slot + proposer assignment
3. Verify blob KZG commitments
4. Sample data-column availability
5. Forward ExecutionPayload to local EL...
8
ENGINE API

EL Validates ExecutionPayload

Each CL node sends the payload to its local EL for full EVM validation. Glamsterdam will move this to engine_newPayloadV5 with block-level access lists.

CL → engine_newPayloadV4(
  executionPayload, blobVersionedHashes,
  parentBeaconBlockRoot, executionRequests
)

// geth: eth/catalyst/api.go
1. Re-execute ALL transactions
2. Verify stateRoot + receiptsRoot
3. Verify gasUsed ≤ gasLimit (60M)
4. Verify blob versioned hashes / commitments
5. Apply EIP-7685 execution requests
// CL separately samples PeerDAS columns + cell proofs

→ { status: "VALID" } or "INVALID"
9
CL

Attestation Phase (t=4s into slot)

Committees of validators vote on what they believe is the correct head of the chain. Pectra's EIP-7549 moved the committee index outside the signed attestation, making aggregation cheaper.

// ~1/32 of all validators attest each slot
Attestation = {
  slot: N,
  beacon_block_root: "0x...", // head vote (LMD-GHOST)
  source: { epoch: E-1, root: "0x..." }, // Casper FFG
  target: { epoch: E, root: "0x..." }, // Casper FFG
  aggregation_bits: 0b1101...,
  signature: BLS_aggregate_sign()
}
// committee_index is outside the signed message (EIP-7549)

// Aggregators combine attestations with same data
// → reduces from thousands to ~hundreds of objects
10
CL

Fork Choice Update (LMD-GHOST)

Each node updates its local fork choice based on accumulated attestations.

// consensus-specs: phase0/fork-choice.md
get_head(store):
  head = store.justified_checkpoint.root
  while has_children(head):
    head = child with max(sum(latest_attestation_weights))
  return head

// Then notify EL about new head:
CL → engine_forkchoiceUpdatedV3({ headBlockHash: new_head })
11
EPOCH

Epoch Boundary — Justification

Every 32 slots (~6.4 min), the epoch boundary triggers justification checks.

// Casper FFG justification
For checkpoint C at epoch boundary:
  votes = sum(effective_balance of attesters voting source→C)
  if votes ≥ 2/3 × total_active_balance:
    C is JUSTIFIED ✓

// Also at epoch boundary:
• Process rewards/penalties for attestation accuracy
• Shuffle committees for next epoch
• Update RANDAO mix
12
FINALITY

Finalization — Irreversible ✅

When a justified checkpoint's child is also justified, the parent becomes finalized.

Epoch N: Checkpoint A justified
Epoch N+1: Checkpoint B justified (with source=A)
→ Checkpoint A becomes FINALIZED 🔒

// Finalized = IRREVERSIBLE
// To revert: attacker needs ≥1/3 of ALL staked ETH
// That ETH would be slashed = destroyed

// Typical time: ~12.8 min (2 epochs) after block
// Long-term research: single-slot finality (SSF)

CL → engine_forkchoiceUpdatedV3({
  finalizedBlockHash: A.execution_payload.block_hash
})
// EL marks the block final; clients may prune stale forks

Anatomy of a 12-Second Slot

How time is divided within each slot

PROPOSE
PROPAGATE
ATTEST
ATT. GOSSIP
AGGREGATE
IDLE
0s2s4s6s8s10s12s
0–2s: Propose
Proposer calls engine_getPayloadV5 → gets ExecutionPayloadV3 from EL → wraps in BeaconBlock → BLS signs → broadcasts via GossipSub.
2–4s: Propagate
Block propagates across the CL P2P network with PeerDAS data columns. Each node validates the block CL-side, then sends ExecutionPayload to its local EL via engine_newPayloadV4.
4–6s: Attest
Committee validators produce attestations: vote on head block (LMD-GHOST) + source/target checkpoints (Casper FFG). Broadcast on per-subnet gossip topics.
6–8s: Attestation Gossip
Individual attestations propagate across subnets. Nodes collect attestations with matching data for aggregation.
8–10s: Aggregate
Selected aggregators combine attestations with identical voting data using BLS signature aggregation → single compact AggregateAttestation. Broadcast on global topic.
10–12s: Idle / Sync
Remaining time before next slot. Nodes finalize fork-choice calculations, sync stragglers. Next proposer begins preparing.

⚡ Coming in Glamsterdam: ePBS changes the slot shape

Enshrined proposer-builder separation (EIP-7732) splits the consensus block from the execution payload and adds a Payload Timeliness Committee (PTC). The payload propagation window grows from ~2s to ~9s, while the 12-second slot and attestation cadence stay the same. Expected with Glamsterdam (Q4 2026, devnets at time of writing).

Finality Deep-Dive — Casper FFG

How blocks go from proposed → justified → finalized

State Transition of a Checkpoint

Example: Finality Over 3 Epochs

Time Event Checkpoint A (Epoch N) Checkpoint B (Epoch N+1)
Epoch N 32 slots processed Proposed —
Epoch N boundary ≥2/3 attested source→A Justified ✓ —
Epoch N+1 32 more slots Justified Proposed
Epoch N+1 boundary ≥2/3 attested A→B Finalized 🔒 Justified ✓

⏱ Time to finality: ~12.8 minutes (2 epochs × 6.4 min) under normal conditions. In practice, a transaction is finalized 2 epochs after the epoch it was included in.

⚔️ Slashing Conditions

Double Vote
Two attestations for different targets in the same epoch.
Attestation 1: target = (E, 0xAAA)
Attestation 2: target = (E, 0xBBB) ← SLASHABLE
Surround Vote
An attestation "surrounds" or is "surrounded by" a previous one.
Attestation 1: source=E1 → target=E4
Attestation 2: source=E2 → target=E3 ← SURROUNDED

🛡️ Safety Guarantee

Once a block is finalized, it cannot be reverted without:

Cost to revert ≥ ⅓ × total staked ETH
≈ ⅓ of all staked ETH · tens of billions of dollars

This is because ≥2/3 voted for the checkpoint. If an attacker finalizes a conflicting checkpoint, at least ⅓ of validators must have double-voted → all slashed.

Liveness vs Safety tradeoff: If >⅓ go offline, the chain stops finalizing (inactivity leak begins) but never finalizes conflicting blocks.

Roadmap: single-slot finality (SSF) is long-term research that would collapse the ~12.8-minute wait into the same slot, without changing the ⅓-slashing safety argument.

Pectra

LIVE · 7 May 2025

Prague (EL) + Electra (CL). Largest EIP bundle of any fork; focused on accounts, staking, and blob capacity.

  • • EIP-7702 — EOAs can delegate to smart-contract code (batching, sponsorship, recovery).
  • • EIP-7251 — max effective balance raised from 32 to 2048 ETH; consolidations supported.
  • • EIP-7691 — blob target/max raised to 6 / 9 per block.
  • • EIP-7002 — validator exits triggerable from the EL.
  • • EIP-6110 — deposits processed on-chain; EIP-7685 execution requests.
  • • EIP-2537 — BLS12-381 precompiles; EIP-7623 — calldata repricing.

Fusaka

LIVE · 3 Dec 2025

Fulu (CL) + Osaka (EL). The blob-scaling fork: data availability sampling plus L1 hardening.

  • • EIP-7594 PeerDAS — nodes custody/sample data columns instead of every blob; ~8× theoretical blob capacity.
  • • EIP-7892 — Blob-Parameter-Only (BPO) forks; blob target raised from 6 toward 10/15, then 14/21.
  • • EIP-7918 — blob base fee bounded by execution cost.
  • • EIP-7935 — default block gas limit 60M; EIP-7825 caps one tx at 16.7M gas.
  • • EIP-7939 — CLZ opcode; EIP-7951 — secp256r1/P-256 precompile for passkeys.
  • • EIP-7917 — deterministic proposer lookahead; EIP-7642 — eth/69 history expiry.

Glamsterdam

DEVNETS · Q4 2026

Gloas (CL) + Amsterdam (EL). Next fork; mainnet date not yet confirmed. Scope is frozen but can still change.

  • • EIP-7732 ePBS — proposer/builder separation enshrined; payload window ~2s → ~9s; adds PTC.
  • • EIP-7928 BALs — block-level access lists for parallel execution and executionless sync.
  • • EIP-8159 — eth/71 block access list exchange; EIP-7975 — eth/70 partial receipts.
  • • EIP-8037 / 8038 — state creation and state-access repricing (reservoir model).
  • • EIP-2780 — cheaper ETH transfers; EIP-7708 — ETH transfers emit logs.
  • • EIP-7997 — deterministic factory at 0x12; EIP-7954 — larger contracts.

Hegotá

PLANNED · 2027

Following Glamsterdam. Scope is not final; these are the changes scheduled so far.

  • • EIP-7805 FOCIL — fork-choice enforced inclusion lists; strengthens censorship resistance.
  • • EIP-8141 Frame Transactions — account-defined validity, native social recovery, sponsored gas.
  • • A natural path toward post-quantum signature schemes and native account abstraction.
  • • Blob scaling, gas-limit increases, and zkEVM/statelessness work continue across forks.

🧭 Long-term direction

Scale L1
Higher gas limits beyond 100M, parallel execution via BALs, ePBS, and zkEVM attester clients.
State & statelessness
The 2026 protocol priorities emphasize binary trees and statelessness long-term. Verkle trees are not on a near-term fork; the MPT remains in production.
Finality & UX
Single-slot finality research, native account abstraction, faster L1 confirmations, and cross-L2 interoperability.
